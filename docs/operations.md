# נוהל עבודה, בדיקות ושחרור

## עקרון

GitHub הוא מקור האמת המתמשך. Issue מגדיר משימה, ענף ו־PR מחזיקים את השינוי, הבדיקות מספקות ראיה דטרמיניסטית, והמסמכים/ADRs משמרים החלטות. שיחת סוכן אינה תחליף לאחד מהם.

## פתיחת משימה

1. פתח Issue אחד ומוגבל.
2. תאר בעיה נראית למשתמש, התנהגות רצויה וקריטריוני קבלה.
3. סמן אם יש השפעת מודל/פרטיות/משפט/תשתית; אם כן, קבל אישור בעלים לפני תחילת המימוש.
4. סווג במפורש: `owner approval required: no` או הסבר מדוע כן.
5. קישור למסמך המוצר, המודל או ADR הרלוונטי.

## מחזור מימוש

1. עדכן `main` וצור ענף לפי `feat/`, `fix/`, `docs/`, `test/`, `refactor/` או `ci/`.
2. קרא `AGENTS.md`, את ה־Issue ואת החוזים המקושרים.
3. הרץ baseline ממוקד.
4. שינוי התנהגות מתבצע ב־RED→GREEN→REFACTOR:
   - כתוב בדיקה ממוקדת.
   - הרץ וודא כשל מהסיבה הצפויה.
   - כתוב מימוש מינימלי.
   - הרץ וודא מעבר.
   - נקה קוד בלי לשנות התנהגות.
5. הרץ `npm run check:fast` במהלך עבודה לפי הצורך.
6. לפני PR יציב הרץ `npm run check:release`.
7. בדוק את ה־diff, היעדר סודות והיעדר שינויי scope לא מאושרים.

## דרישות PR

ה־PR כולל:

- קישור ל־Issue (`Closes #N`).
- סיכום קצר של השינוי וה־out-of-scope.
- סיווג אישור בעלים.
- ראיית RED ו־GREEN כאשר הייתה התנהגות חדשה.
- תוצאת `npm run check:release`.
- צילומים או ראיה חזותית בשינוי ממשק.
- סיכונים, תאימות לאחור ושיטת rollback.
- עדכון docs/ADR/status אם ההתנהגות או ההחלטה השתנו.

## שערים קנוניים

```bash
npm run check:fast
npm run check:full
npm run check:release
npm run build
```

`check:release` הוא שער השחרור המקומי: בדיקות מונחים, lint, יחידה/רכיב, typecheck/build ובדיקות Playwright מול תוצר production.

GitHub workflow `בדיקות איכות` חייב לעבור לפני מיזוג. Workflow הפריסה מריץ שוב `check:release` ב־main לפני העלאת artifact ל־Pages.

## מיזוג ופריסה

1. ודא שהענף מעודכן ושכל הבדיקות הנדרשות ירוקות.
2. אם נדרש אישור בעלים, האישור חייב להתקבל לפני תחילת המימוש וגם להישאר תקף ל־scope הסופי לפני המיזוג. אם הצורך מתגלה באמצע משימה רגילה, עוצרים לפני שינוי נוסף ושואלים.
3. מזג ב־squash ומחק את הענף הממוזג.
4. בדוק את ריצות `בדיקות איכות` ו־`פריסה ל-GitHub Pages` ב־main.
5. בשינוי משתמש, אמת חיצונית באופן דטרמיניסטי:

```bash
npm run verify:live
```

6. הפקודה משווה את `build-commit` שבאתר ל־commit הנוכחי של `main`, ודורשת HTTP 200, כותרת מוצר צפויה, לפחות module script אחד, לפחות stylesheet אחד ו־assets לא ריקים. לכן גם פריסה ירוקה של גרסה ישנה נכשלת באימות. Action ירוק לבדו אינו הוכחת אתר חי.
7. עדכן `docs/status.md` כאשר גרסה, מגבלה או מצב שחרור השתנו.

## כשל ו־rollback

- אין להסתיר, לעקוף או לתאר כשל כ“כמעט עבר”.
- כשל לפני מיזוג: תקן בענף עם regression test והריץ מחדש את השער המלא.
- כשל אחרי מיזוג: פתח Issue ו־PR revert או תיקון ממוקד; אל תדחוף ישירות ל־main.
- שמור קישורים ל־run הכושל ול־run המתוקן ב־PR/Issue.
- שינוי repository setting מהותי מתועד לפני ואחרי, כולל דרך חזרה להגדרה הקודמת.

## מטריצת אישורים

קודקס רשאי לבצע עצמאית תיקוני באגים, בדיקות, refactor, תיעוד, נגישות ו־responsive UI כל עוד החוזים נשמרים.

אישור בעלים נדרש לשינוי בנוסחה, בתהליך האקראי, בהנחות, במשמעות preset, בהגדרת מדד, בפרטיות, analytics, cookies, disclaimer, שירות/עלות, secrets, תשתית או אינווריאנט מוצר.

אסור תמיד: commit של secret/מידע אישי, זיוף בדיקות, direct push ל־main או טענת הצלחה ללא בדיקת GitHub והאתר החי.

## תבנית דיווח סופית

דווח בעברית ובקצרה:

- ענף ו־commit.
- PR וקישור.
- בדיקות ממוקדות ו־release.
- מצב GitHub CI.
- מצב merge.
- מצב Pages ובדיקת האתר החי.
- החלטה/פעולת בעלים שנותרה, אם יש.
